## 一、正确实现：客户端插件的最小契约

### 1.1 包声明

```json
{
  "name": "your-plugin",
  "exports": { ".": "./lib/index.js", "./client": "./lib/client.js" },
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" },
    "client": {
      "platform": "web",
      "inject": ["@deepseek-ai/dsh-client-ui-chat"]
    }
  }
}
```

- `client.inject` 是**模块加载顺序**（先加载谁），不是 cordis 服务注入——两者同名但语义不同，会分别出现在 `package.json` 和 bundle 代码里
- `exports["./client"]` 是宿主找到产物的路径，产物由宿主在 `/plugins/<pkg>/client.js` 提供

### 1.2 bundle 顶层：一个字符都不能错

```js
window.__ModuleLoader__.load({          // ← 双下划线，且必须是顶层同步调用
  id: "your-plugin",
  factory: (require) => {
    const module = { exports: {} };
    const exports = module.exports;
    var React = require("react");       // ← 默认导入 = 整个模块对象
    var { createRoot } = require("react-dom/client");   // ← 具名导入才取属性

    const inject = ["slots"];           // ← cordis 要注入的服务名
    function apply(ctx) { /* 挂载 */ }
    ctx.effect(() => () => { /* teardown */ });

    exports.apply = apply;
    exports.inject = inject;
    return module.exports;
  },
});
```

**四条不可违反的规则：**

| # | 规则 | 违反的后果 |
|---|---|---|
| 1 | 全局名是 **`window.__ModuleLoader__`**（双下划线） | 单下划线 = 未声明标识符 → `ReferenceError` → **应用拒绝启动** |
| 2 | 必须在**顶层同步**调用 `load()` | 轮询/延迟注册 → `loaded without registering "<id>" via __ModuleLoader__.load` |
| 3 | 必须导出 **`apply`**（不是 `install`） | `invalid plugin, expect function or object with an "apply" method, received object` |
| 4 | 默认导入绑定**整个模块对象** | `require("react").React` 是 `undefined` → 渲染时 `Cannot read properties of undefined (reading 'useMemo')` |

第 4 条尤其阴——**它在注册阶段不报错**，只在组件真正渲染时崩，报错信息还指向 React 内部。

> 官方 57 个客户端 bundle 全部是 `window.__ModuleLoader__.load(` 开头。
> 想确认正确形态，直接读任意官方产物的头尾：
> ```bash
> node /tmp/ae.js "/Applications/DeepSeek Harness.app/Contents/Resources/app.asar" \
>   cat "/dsh/node_modules/@deepseek-ai/dsh-client-ui-goal/lib/client.js" | tail -c 400
> ```
> （`/tmp/ae.js` 是 asar 读取脚本，见 §3.3）

### 1.3 插槽遮蔽：怎么改内置渲染而不改数据

DSH 的推理文本不是独立节点，而是 `assistant-step` 节点里的一个 **block kind**，由
`assistant/live-chunk` 的 `reasoning-delta` 增量累加而来。

要接管它，注册一个**同 key、更低 priority** 的插槽条目，包裹内置渲染器：

```js
ctx.slots.register(
  { name: "conversation.chat.node", key: "assistant-step", priority: -1, locale: "chat", inject },
  Shadow,   // 你的组件：改 reasoning 块，其它块按引用原样透传
);
```

**运行时规则：同一个单元格里 priority 最小者生效。**
这条规则**不在文档里**，是从行为反推出来的：注册 `priority: -1` 后，
`ctx.slots.entriesOfSlot("conversation.chat.node")` 的第一项就变成了 `assistant-step@-1`。

内置条目的 `component` 与 `inject` 都可以读出来复用：

```js
const builtin = ctx.slots.entries(SLOT).find((e) => e?.options?.key === KEY);
builtin.inject;      // 转发给出口，保持内置行为
builtin.component;   // 需要时作为 fallback
```

**关键设计收益**：走 React 自己的渲染，**完全不碰会话记录**。模型下一轮收到的仍是它自己的原始
推理，会话日志、轨迹、导出文件全都是原文——翻译只是显示层。

### 1.4 状态：用服务注入，不要等 Object

```js
// ❌ 错：ctx.slots 在注册时可能还没物化
// ✅ 对：声明 inject，cordis 等依赖就绪后才调 apply
const inject = ["slots"];
function apply(ctx) { /* 这里 ctx.slots 一定可用 */ }
```

宿主半区（`lib/index.js`）用 `root.inject([...])` 分两段装配，因为路由只需要 web 服务，
而引擎还需要 LLM 服务（可能不存在，例如只用 Ollama 的部署）：

```js
root.inject(["webServer"], () => { /* 挂路由 */ });
root.inject(["llm"], () => { /* 重建引擎 */ });   // 分开，任一缺失不影响另一个
```

## 二、环境与宿主：不会写在文档里的行为

### 2.1 触发致命错误的条件

应用对启动失败的处理是**全有或全无**：任何一个 entry 没激活，就弹出「应用无法启动或已意外停止」，
并提供三个按钮（重启 / 禁用第三方插件并重启 / 退出）。

**实测：即使语法完全正确的 bundle，也可能让应用无法启动。** 组合运行在一个共享环境里，
一个成员抛错可以带走整条组合。

> 我的插件曾在某条组合里被别的包抛出的 `ReferenceError` 连带致死——
> 崩溃日志指向 `index-5SrrfWpU.js:5855`，那是 **DSH 自己的 bundle**（官方产物 711 行不可能报出 5855 行）。

### 2.2 恢复模式会重写你的配置

**这是最需要警惕的行为。** 触发一次启动失败后：

| 文件 | 被改成什么 |
|---|---|
| `package.json` | `bundles` 被清成只剩 `base + web-app`；你的依赖全没 |
| `cordis.patch.yml` | 只剩设置项；**你手写的 provider 配置（如本地 Ollama 路由）一起消失** |

**后果**：用户装一个第三方插件 → 启动失败 → 恢复模式**抹掉他手写的全部配置**。

原文件会备份成 `cordis.patch.yml.bak-<毫秒时间戳>` / `package.json.bak-<时间戳>`，
可以从中恢复。**开发期间请务必备份一份自己的干净 patch**，每次恢复后从备份重建。

> 我在一次会话里被恢复模式清空过三次，每次都丢掉了 Ollama 配置。

### 2.3 启动图是快照，刷新页面无用

宿主的启动图（compose 结果）在**应用启动时**确定。装完插件后：

- ❌ 刷新页面 → `entries` 数量不变，插件不出现
- ✅ **完全退出并重新打开应用** → 重新组装

实测：`Page.reload` 前后 `__DSH_BOOT__.entries.length` 完全一致（67 → 67）。

### 2.4 两种形态的注入方式不同（这解释了"本地能跑、装上就崩"）

| 形态 | 注入方式 | 顺序安全性 |
|---|---|---|
| Web 宿主（`dsh --profile <p>`） | 把注入行写进 HTML，浏览器按依赖顺序解析 | 天然有序 |
| 桌面壳（Electron） | `script` 行由壳**同步 append**，不 await | 存在早执行窗口 |

所以**在 Web 宿主上验证通过，不能证明桌面端能跑**。我在这上面浪费了整整一轮调试。

### 2.5 单实例与调试端口

- 应用是**单实例**：已经有实例在跑时，从终端再启动一个不会产生新 renderer
- 崩溃日志在 `~/Library/Logs/DeepSeek Harness/crash-*.log`
- 宿主的错误报告**可能只写 `see console`**，具体原因要读 renderer console（见 §3）
- `ELECTRON_ENABLE_LOGGING=1` 对本应用**无效**，拿不到 renderer 输出

## 三、调试手段：没有它就只能盲改

### 3.1 远程调试端口（**最高优先级**）

```bash
"/Applications/DeepSeek Harness.app/Contents/MacOS/DeepSeek Harness" \
  --remote-debugging-port=9222 --remote-allow-origins='*'
```

然后从 Node 连 CDP：

```js
const list = await (await fetch("http://127.0.0.1:9222/json/list")).json();
const page = list.find((t) => t.type === "page");
const ws = new WebSocket(page.webSocketDebuggerUrl);
```

可以做到：

- 读 `Runtime.consoleAPICalled` / `Runtime.exceptionThrown` —— **拿到宿主丢弃的错误原因**
- `Runtime.evaluate` 读页面状态：`__DSH_BOOT__.entries`、DOM 结构、你的插件暴露的运行时对象
- `Page.reload` 强制重新渲染（不用重启应用）

> **这是整个项目的转折点。** 在开它之前我改了五轮代码、让用户重启了七八次，全在盲改；
> 开了之后，剩下的两个 bug 都是直接读出来的。

**建议：插件在 `apply()` 里挂一个 `globalThis.__yourPlugin = runtime`**（含诊断字段），
调试时一个 `Runtime.evaluate` 就能问出内部状态，不用猜。

### 3.2 读 asar 里的官方实现

官方包都在 `app.asar` 里。写个读取脚本比反复猜 API 靠谱得多：

```js
// /tmp/ae.js —— 用法: node ae.js <asar> ls|cat <内部路径>
const fs = require("fs"), P = process.argv[2];
const fd = fs.openSync(P, "r"); const b = Buffer.alloc(16); fs.readSync(fd, b, 0, 16, 0);
const jsonLen = b.readUInt32LE(12); const jb = Buffer.alloc(jsonLen);
fs.readSync(fd, jb, 0, jsonLen, 16);
const h = JSON.parse(jb.toString("utf8")); const base = 16 + b.readUInt32LE(4);
const find = (p) => { let n = h; for (const x of p.split("/").filter(Boolean)) { if (!n.files?.[x]) return null; n = n.files[x]; } return n; };
const n = find(process.argv[4]);
if (process.argv[3] === "ls") for (const [k, v] of Object.entries(n.files || {})) console.log((v.files ? "D " : "F ") + k);
else { const o = Buffer.alloc(n.size); fs.readSync(fd, o, 0, n.size, base + Number(n.offset)); process.stdout.write(o); }
```

`README.zh.md` 是官方包的**中文文档**，很多行为在那里有明确定义——**先读文档再读代码**。

### 3.3 安装前硬闸门

**永远不要把"没验证过的产物"装进用户的 profile。** 我的 `scripts/smoke-client.mjs` 做四件事：

1. 断言产物以 `window.__ModuleLoader__.load({` 开头、且不含裸 `_ModuleLoader__`
2. 断言没有轮询/延迟注册
3. 用假 loader 求值，断言**立即**注册、`id` 正确
4. 调 `factory()` 拿到导出面，断言有 `apply`/`inject`，并**实际调用一次 `apply(ctx)`**

失败就 exit 1，安装脚本直接拒绝。

**反向验证是必须的**：故意把每一条改坏，确认闸门能拦下。我做过四次，每次都拦住了。

### 3.4 构建与安装的原子性

**不要边改边让用户重启。** 我犯过两次：重建 `lib/client.js` 的中途用户重启，
应用读到**写了一半的文件**，报 `import failed`。

正确顺序：**改完 → 跑测试 → 安装 → 一次性通知用户重启**。

## 四、性能：流式场景的两个致命陷阱

### 4.1 陷阱一：翻译调度被自己饿死（客户端）

流式翻译的朴素实现是"文本变了就防抖 450ms 后发请求"。**这个朴素实现会饿死。**

我最初的写法：

```js
if (timerRef.current !== null) return undefined;              // ① 有定时器就返回
if (length - (stateRef.current.at ?? 0) < MIN_GROWTH) return; // ② 比"上次成功返回"的长度
```

- **①** 定时器只在首次挂载时排一次。流式期间文本一直在长，那个定时器一直没触发完
- **②** 下一个请求必须比"上一次**成功返回**"的长度多 24 字符——响应越慢，基准越旧，越难满足

**实测后果**：单次调用空载 1.5 秒，**流式时 50–85 秒**。

正确的写法是**尾沿防抖 + 背压**：

```js
const send = () => {
  const snapshot = textRef.current;   // ← 触发时才读，永远发最新全文
  sentRef.current = snapshot.length;
  post("/translate", { key: identity, text: snapshot }, signal);
};
const arm = () => {
  timerRef.current = setTimeout(() => {
    timerRef.current = null;
    send();
    // 只有"自上次发送后确有增长"才续期：长流不被饿死，静止的块只花一次请求
    if (textRef.current.length - sentRef.current >= MIN_GROWTH) arm();
  }, TICK_MS);
};
```

要点：**在触发时读最新文本**，防抖期间到达的内容全都包含进去，**中间态根本不发**（这就是背压）。

**修复后实测**：并发 12 条，总耗时 3.3 秒，中位 1.0 秒。

### 4.2 陷阱二：宿主并发闸门设得太小

```js
const MAX_INFLIGHT = 2;   // 我自己设的，太小
```

单次 1.5 秒 × 大量流式请求 → 排队迅速积压。**实测**空闲宿主 1.7–2.2 秒，
有 UI 流量时 50–85 秒。调到 4 后并发 12 条 3.3 秒完成。

> 排查方法：**起一个空载宿主做对照实验**。同样的调用，空载快、有负载慢
> → 问题在排队/调度，不在模型。这一步能直接把"模型慢"和"我把模型用错了"分开。

### 4.3 缓存要按内容去重，不要按位置

流式翻译的正确缓存键是**原文整句**，不是节点位置。这样同一句在不同会话/节点里重复出现时免费。

```js
rememberTranslation(identity, sourceLength, translated);
newestTranslation(identity, length);   // 允许源文本增长，取 ≤ 当前长度的最新译文
```

**必须设上限**：我的缓存 4000 条 / 约 1.9 MB，满了按最旧淘汰。没有上限会无限增长。

## 五、本地模型：路由与硬约束

> 本机（M1 Pro / 32 GB / GPU 上限 24.5 GiB）实测数据。

### 5.1 路由速查

| 任务 | 模型 | 解码 | 显存 |
|---|---|---|---|
| **翻译 / 改写 / 摘要 / 分类** | **`qwen2.5:1.5b`** | **93.1 tok/s** | **2.1 GB** |
| 翻译备选 | `qwen3:1.7b` | 87.3 tok/s | ~3 GB |
| 跑命令、多轮工具调用的 agent 循环 | `qwen3.6:latest` | 38.8 tok/s | ⚠️ 23.4 GB |
| 难题（算法/数学/复杂重构） | `qwen3.8:latest` | 6.5 tok/s | 18.1 GB |
| 图片 / 音频输入 | `gemma4:12b` | 11.5 tok/s | 8.0 GB |
| **不用** | `qwenlong-l1.5-abliterated` | 42.0 tok/s | ~19 GB |

### 5.2 硬约束（不要试探）

1. **`gemma4:12b` 禁止执行 shell / 多参数工具调用。** ollama 的 gemma4 renderer 会**静默丢弃**
   与 schema 关键字同名的参数（`description`/`type`/`properties`/`required`/`nullable`），
   DSH `bash` 的必填 `description` 必然丢失 → 调用失败。上游修复 PR 未合入，DSH 侧无法规避。
2. **`qwen2.5:1.5b` 禁止传任何思考参数。** Ollama 0.35.1 对不支持思考的模型传 `think:true`
   直接 HTTP 400。
3. **`qwenlong` 不要用**：思考开关失效，中文占比仅 35%。
4. **思考模式首字延迟 35–51 秒。** 要低延迟就别开思考。
5. **`qwen3.6` / `qwenlong` 容易"停不下来"**（未收敛率 45% / 44%），派活要给足 `maxTokens`。
6. **别同时驻留两个大模型**（超 24.5 GB 走 swap，延迟抖动可达 18 倍）。
7. **Ollama 升级后可能出现半初始化坏状态**（`timed out waiting for llama-server to start`、
   流式请求挂死）→ **重启 Ollama App** 即可恢复。

### 5.3 反直觉发现：Qwen3.6 / 3.8 不适合"每次都是新文本"的任务

它们是 **Gated DeltaNet 混合线性注意力**，循环状态无法回退到任意前缀位置，
llama.cpp 只能**整段重算**提示词：

| 模型 | 完全重复提示词 | **换新片段（流式翻译的真实场景）** |
|---|---|---|
| qwen2.5:1.5b | 1 tok / 12ms | **20 tok / 44ms**（只重算新片段） |
| qwen3.8:latest | 4 tok / 320ms | **332 tok / 5814ms（全量重算）** |

**"系统提示词固定 ⇒ 前缀缓存必然命中"这个直觉在这里不成立**——因为每次请求的**尾部**都是新文本。

## 六、发布前检查清单

如果你的插件要让**陌生人**安装，下面每一条都是前提。

### 安全底线

- [ ] **客户端 bundle 顶层加防御**：任何异常都不能冒泡成致命启动错误
      （否则对方应用直接开不了，而恢复模式还会**抹掉他手写的配置**）
- [ ] 补 `dsh.compatibility` 声明，让市场能标出不兼容版本
- [ ] 验证 `dsh plugin --profile <p> add <pkg>` **标准安装路径**
      （别只测自己的软链脚本——那条路我没测过）
- [ ] 一键卸载 + 出错自救说明（引导用户点恢复对话框中间那个按钮）
- [ ] 说明首次使用需要配置什么（不能假设对方有 Ollama）

### 兼容性风险（必须承认的债）

客户端插件深度依赖**没有稳定性承诺的内部约定**：

| 依赖 | 变更后果 |
|---|---|
| 插槽键 `conversation.chat.node` / `assistant-step` | 改个名就失效 |
| **最小值优先**的遮蔽规则 | 实测得出，不在文档里 |
| 内置条目的 `inject` 契约 | 变了我这层就崩 |
| 事件流形状（`reasoning-delta`、block kind） | 变了我这层就崩 |

**结论：每次 DSH 升级都需要重新验证。这是持续维护债。**

### 发布配置

- [ ] GitHub 仓库 + `dsh-plugin` topic（插件市场按这个 topic 发现）
- [ ] `package.json`：去掉 `private`、加 `repository`/`keywords`/`version`
- [ ] `LICENSE` + `PROVENANCE.md`（参照 `dsh-whale-widget` 的形态）
- [ ] README 中英双语
- [ ] 说明翻译质量取决于所选模型 + 已知淘汰名单

## 七、方法论：我犯过的错

这一节比前面六节都重要。上面每一个 bug 都是**可以避免的**。

### 7.1 拿"在更宽松环境里能跑"当验证

我的 Web 宿主把注入行写进 HTML，浏览器按依赖顺序解析；桌面壳是**同步 append**。
我在 Web 上验了七八轮全过，桌面一装就崩。

**教训**：目标环境的行为**必须单独验证**。宿主不同 ⇒ 加载语义不同 ⇒ 结论不可迁移。

### 7.2 用 mock 掉了正要验证的东西

测试里装了 `_ModuleLoader__` 的 stub，于是**既没发现拼写错误、也没发现加载顺序问题**——
因为 stub 把这两个真实约束都抹平了。

**教训**：mock 的边界决定了测试的能力上限。被 mock 掉的那一层，**永远不要假设它是对的**。

### 7.3 把错误归属搞反了

崩溃日志里那行 `ReferenceError: _ModuleLoader__ is not defined` 指向 `index-...js:5855`。
**那是 DSH 自己的 bundle**（我的产物 711 行，不可能报出 5855 行）。我却按它改了自己的代码，
凭空调出一个"轮询延迟注册"的新 bug，然后为它 debug 了整整一轮。

**教训**：报错的位置信息**先验证归属**。看行号、看文件、看是不是自己的产物。

### 7.4 边改边让用户重启

两次让用户读到了**写了一半的文件**。这是操作顺序问题，不是技术问题，但代价由用户承担。

**教训**：改完 → 测试 → 安装 → **一次性**通知。

### 7.5 跳过二分

从头到尾没验证过"桌面端到底能不能接受一个最小的第三方客户端 bundle"，
一直在改完整插件。后来**三个探针、一次重启**就定位了。

**教训**：大而复杂的失败面前，先做**最小可验证实验**把问题空间切开。

### 7.6 只验证"注册"不验证"渲染"

所有测试都只断言"插槽注册成功"，没有一条断言"组件能渲染出来"。
于是 `require("react").React` 这种错误**一路溜到了应用里**才被发现。

**教训**：验证要覆盖**到用户能看见的那一层**。注册成功 ≠ 功能可用。

### 7.7 测量方法本身出错

我一度报告"29/32 行有两个摘要元素"，结论指向插件重复渲染。
实际是**选择器把 `_summary` 容器和它内部的 `_summaryText` 都数了**——
那是正常 DOM 结构。**是我的测量错，不是插件的问题。**

**教训**：测量结果与预期不符时，**先怀疑测量方法**，再怀疑被测对象。

### 7.8 最有效的一步

**开远程调试端口。**

在它之前：改了五轮代码、让用户重启七八次，全靠猜。
在它之后：剩下的 bug 都是**直接读出来的**，每次定位不超过几分钟。

**教训**：**先建立可观测性，再动手改。** 盲改的成本是指数级的。
